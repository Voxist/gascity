# Load test — direct ServerMode validation + capacity wall (2026-06-10)

Satisfies the city-scale plan's **"load harness FIRST"** gate (P2.1). Run after
switching voxist-city to `[beads] proxied=false` (direct ServerMode), to validate
the store path and find the real ceiling for "8 rigs active simultaneously."

## 1. Modeled harness (P2.1, `test/loadharness`, `go test -tags loadharness -run TestCityLoad`)

Deterministic model of the controller's spawn/fan-out cost. Confirms structural
invariants, not absolute numbers.

| scenario | scopes | sessions | spawns/min | fan-out | tick p50 |
|---|---|---|---|---|---|
| idle-baseline | 8 | 0 | 192 | 0 | 48ms |
| amplifier-100-sessions | 8 | 100 | 4992 | 800 | 2.45s |
| mail-fanout (50 rcpt) | 4 | 10 | 1536 | 40 | 544ms |
| poison-repro / server-fail / type-reject | 4 | 10 | — | — | — |

The three fault scenarios show `degraded_ticks=10` — faults are **detected, not
silent-empty** (the type-reject case is caught by the write-probe, which the
transport breaker misses).

## 2. Real load probe — reads (live direct store)

| concurrency | success | p50 | p95 | peak conns | new i/o-timeouts |
|---|---|---|---|---|---|
| 40 | 40/40 | 1.5s | — | 69/256 | 0 |
| 80 | 80/80 | 4.1s | 4.6s | 169/256 | 0 |

**Direct ServerMode handles concurrent reads cleanly.** Zero i/o-timeouts vs the
35,651 accumulated during the proxy era — the db-proxy stall failure mode is gone.
Baseline connections dropped 32→2 (direct mode releases promptly; the proxy held a
stale pool). Latency scales with concurrency (bd-subprocess-per-op cost); the
Ready fan-out collapse keeps the controller's per-tick bd count low.

## 3. Real load probe — writes (the limiting finding)

Every `bd` write is a **Dolt commit**; concurrent commits to a *single database*
contend hard.

| test | success | failure mode |
|---|---|---|
| single write | ✓ | — |
| 20 concurrent, distinct rows | 10/20 | `dolt commit: invalid connection`, p50 13.6s |
| 40 concurrent, 8 rows (5/row) | 8/40 | Error 1213 serialization + invalid-connection |

- 0 i/o-timeouts (so it's commit contention, **not** the proxy stall — direct mode
  is still correct).
- **`bd` does not retry** transient commit conflicts (1213 / invalid connection) —
  a failed claim is silently lost. Under a burst claim-storm in one scope, claims
  fail → beads stay open → `in_progress` stalls. → **bead `vc-r5z3ga`**.
- Mitigation: 8 rigs are separate DBs (separate commit graphs → cross-rig writes
  don't contend); keep per-scope concurrent writes low. The risk is concentrated
  burst claims within one hot scope.

## 4. The capacity wall (root cause of order-dispatch starvation)

While load-testing, the controller was found **crash-looping**: SIGKILLed +
KeepAlive-respawned every ~8 min (launchd `LastExitStatus=9`), API calls taking
3–33s, process-table snapshots timing out (`signal: killed`).

Cause — the **box is catastrophically overloaded**:
- load avg **~125**, **1522 processes**, **127 GB / 127 GB RAM** (239 MB free).
- dominant cost: **~44 concurrent `go build` / `go test` at ~2.1 GB each** (the
  executors building gascity in worktrees) + 320 node + 200 tmux + 61 claude.

Consequence: city-scoped orders on a 2-min cooldown (unrouted-feeder, phase-feeder,
gate-sweep) can't fire reliably — the controller never stays alive/responsive long
enough. Fresh unrouted beads (e.g. vw-pph0) stay unrouted. → **bead `vc-pxlhvw`**.

`max_active_sessions=48` bounds session **count** but not per-session RAM (~2–4 GB
when an agent is building) — 48 building sessions can exceed 128 GB.

## Conclusions / recommendations

1. **`proxied=false` (direct ServerMode) is validated** — reads scale to 80
   concurrent at 100%/0-timeouts; keep it until the v2 db-proxy stall is fixed.
2. **RAM-derive `max_active_sessions`** from measured RSS-per-building-session
   (this run IS the P0.2 capacity drill: ~2–4 GB/agent → cap ~20–30 on a 128 GB
   box, not 48).
3. **`bd` commit-retry** on 1213 / invalid-connection (`vc-r5z3ga`) — turns lost
   claims into eventually-successful ones.
4. **Reap orphaned processes** — 200 tmux for ~13 sessions is heavy leakage;
   reaping relieves the box.
5. **Protect the controller** from SIGKILL under load (oom/nice priority) so order
   dispatch survives load spikes (`vc-pxlhvw`).

Methodology note: `bd` (server) is authoritative; direct `dolt sql` on `.beads/dolt`
reads a *lagging* on-disk working set — use `bd` for live counts.
